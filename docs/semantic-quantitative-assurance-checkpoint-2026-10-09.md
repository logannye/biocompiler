This completes the source implementation of the four remaining user-approved
items on `codex/dev-policy/semantic-foundation-v2`. See the
[versioned assurance contract](policy-quantitative-assurance-v0.1.md) for the

## Delivered scope

1. A selected coordinator and separately owned private reservoir components
   communicate through checked edge-allocation signals and atomically committed
   state updates. The complete bounded grid checks ordered reservation,
   ownership, transport, conservation and effect requests. Two to four binary
   reservoir shapes are admitted; the principal exact RNA example selects four
   components for three reservoirs and one coordinator.
2. Explicit finite parameter uncertainty and exact rational error bounds are
   checked over every reachable synchronized state pair and every prefix of the
   declared horizon. Named relations compose through byte-exact intermediate
   endpoints and the triangle rule. Every action request must still agree
   exactly, and all ten existing exact refinement relations are retained.
3. Supplied measurement criteria and dossiers bind complete selected component,
   mechanism, parameter and environment identities. Protocol, dataset, analysis,
   provenance and raw replicate intervals remain inspectable. Recomputed
   interval compatibility is separate from model correspondence and biological
   function. The latter remains unassessed; fixtures are explicitly synthetic.
4. A complete original assurance request travels through fresh compile, check,
   replay and export. Optional approximation and explicitly required evidence
   gates cannot authorize output from a saved PASS. Exact material construction
   remains the existing accepted-only path, with its original RNA and manifest
   retained inside the assurance manifest.

Python facades snapshot their inputs and expose typed immutable descriptions;
the native checker owns admission and private checking capabilities. Capability
planning remains advisory. Old profiles retain their original exact behavior.
Unsupported state sizes, clocks, uncertainty sets and component arrangements
fail explicitly instead of silently weakening the specification.

## Validation and acceptance boundary

Focused local tests exercise typed authoring, immutable transport, adversarial
report binding, deterministic fixtures, runner accounting and source inventories.
They do not execute native proofs. Strict typing and dependency checks remain
part of the source gate. No local OCaml/Rust build or native execution was used.

The complete development runner now contains 55 native suites. The full bundle
contains 195 Dune suites, 203 executable entries and 36 original fixtures, with
77 ordered fixture-dependent suites. The existing ten SDK campaigns retain all
260 observations; quantitative assurance adds a distinct 21-observation actual
Core/Verify campaign. Installed acceptance uses the same owned wheel environment
and binaries and checks the imported Python modules against their installed
RECORD entries. Four platform/Python slots retain separate evidence.

Acceptance requires a successful coherent hosted development run, the complete
integration workflow including installed-package and cross-platform checks,
merge, and fresh actual-main validation. The integration pull request and its
GitHub runs bind these claims to exact source, platform, run and attempt.
Earlier passing or failed runs never qualify a later source revision. The
initial recovered checkpoint's preflight/compiler failures are preserved as
diagnostic lineage, not acceptance.

The remaining long-term extensions are richer reservoir grids, multiple clocks,
delayed transport, continuous uncertainty, additional physical coordination
contracts and authenticated experimental artifact ingestion. They are outside
this bounded profile and require new explicit semantics and evidence.
