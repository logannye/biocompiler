# Reference manager reuse and historical results

The same native reference manager can retain multiple Molecular attempts. Each
attempt has a distinct physical capability and immutable captured provider roots;
starting another attempt neither copies nor resets the actual manager. Original
manager dependency writes, duplicate profile failures and partial state remain
observable in their original order. This is a compatibility source checkpoint,
not complete public-manager or release acceptance.

Preparation enters a bounded LIFO continuation scope. The exact capability leaves
that scope after success or failure. A command saves its active attempt before
calling user code, so nested callbacks cannot retarget its completion notice.
Failed preparation and cleanup do not replace an already active user exception.
Closed or invalidated channels cannot reconnect or mint new authority.

The Python facade retains separate host roots and stable emission/proposal
callables per attempt. Native provider identities bind the exact preparation and
provider role. Host proposals remain opaque until the native workflow independently
checks them. Final-source readers retain the original two reads, including nested
finishes. Complete raw cleanup frames are counted separately from the historical
439 manager operations; no traffic is clipped to force the original count.

Completed Builds remain physical historical capabilities. A package extension can
retrieve a Molecular Build only from its actual channel and exact completed Build
identity. It cannot import a Python record, reconstruct acceptance, or silently
select a different latest result. Kind-only compatibility lookup follows successful
completion order. The existing cumulative work and retained-data lifetime covers
all attempts without refunds or a fresh owner for old retained state.

The original 18-method campaign, 27 initializations, 439 manager operations and
1718 internal observations remain unchanged. New finite source witnesses restore
the complete Core source through counterpart v4 to the preceding v3/v2/v1 chain,
and restore all 31 changed facade spans. Runtime-sites v5 records actual Python
3.11 and 3.14 source origins. Earlier witnesses, original test bodies and frozen
expected values are preserved. Repaired-frame mutants exercise wrong providers,
preparations, historical Builds and missing or extra scope cleanup.

The draft passed 175 Python controls per supported runtime and strict checking of
27 Python modules before integration. The integrated tree also passes all 175
controls and 13 inventory checks on each runtime, with strict checking of the
same 27 modules. Discovery agrees on 3310 tests across 332 classes; discovery
is not full execution.
Dune and hosted CI retain all earlier suites and add the 118th suite for real
native attempt ownership, state, scopes, old providers and historical results.
Native compilation and execution remain hosted-only. Complete current installed
replay, both platform jobs, four-runtime reconstruction and release accounting
remain required; source tests are not native execution.

Ordinary pre-existing Python managers, generic managers without reference
initialization, subclasses and duck-typed manager ownership remain separate open
migration work. Python semantic fallback or importing a formerly accepted Python
record cannot close those requirements. Package public transport and independent
package verification also remain separate. Python remains the production default.
